# Gates 3.1, 3.2, 3.3 — queue and journal on real flash, across a real reset

| | |
|---|---|
| Date | 2026-08-31, evening |
| Node | **B**, `89EF45670123ABCD` — first sketch we ever put on this board |
| Sketch | 16, `firmware/src/bringup/sketch_16_storage.cpp` |
| Firmware | `maxl-bringup-0.1.0-ga69f2ef` |
| Build | `bringup` (debug), PlatformIO |
| Reset | real `NVIC_SystemReset()`, not a soft path |

**Result: 3.1 passes. 3.2 and 3.3 fail.** This is the first time sketch 16 has ever run --
it is the sketch that took node A off the USB bus on 2026-08-31 with a stack overflow, and
it had never reached its own far side before today.

## Gate 3.1 — queue survives reboot with 20 pending messages: PASS

```
RESULT phase                 = after
RESULT store.mounted         = 1
RESULT after_reset           = 1
RESULT g31.restored          = 20
RESULT g31.all_present       = 1
RESULT g31.order_preserved   = 1
RESULT g31.no_duplicates     = 1
RESULT gate_3_1.pass         = 1
```

Twenty messages written before the reset, twenty back after it, in order, none doubled.
`docs/test-plan.md` 3.1 asks for exactly that.

## Gate 3.2 — queue full behaviour: FAIL

```
RESULT g32.size_at_capacity            = 24
RESULT g32.evicted_oldest_delivered    = 1
RESULT g32.kept_undelivered            = 1
RESULT g32.refused_when_none_delivered = 0
RESULT gate_3_2.pass                   = 0
```

Two of the three criteria hold: a full queue drops the oldest *delivered* message and keeps
undelivered ones. The failing one is the case where nothing has been delivered yet and there
is therefore nothing safe to evict -- the queue is expected to refuse the new message rather
than drop an undelivered one, and it did not.

## Gate 3.3 — journal wraparound: FAIL

```
RESULT g33.held                    = 0
RESULT g33.capacity                = 128
RESULT g33.lost                    = 0
RESULT g33.oldest_survivor_correct = 0
RESULT g33.reclaimed_on_ack        = 0
RESULT gate_3_3.pass               = 0
```

The journal holds nothing at the point the check runs, so nothing about wraparound is
exercised. `g33.held = 0` against a capacity of 128 is the shape of a check that never got
its fixture, not of a wraparound that went wrong.

**Not yet determined: whether the fault is in the sketch or in `app/`.** Both readings are
open, and the evidence does not settle it:

- For the sketch: the journal region has a history of exactly this. On 2026-08-31
  `exerciseRegion` in sketch 10 carried 64-byte buffers against a 70-byte
  `app::kJournalRecordBytes`, so the journal region fell into a "skipping the round trip"
  branch on every run while the report looked like a success.
- For `app/`: the host suite covers both classes (254 cases, 451 223 assertions, all green)
  and the two-node simulation adds 7224 + 16 checks. That is evidence the logic is
  self-consistent, not that it is right on this hardware.

Next step is to read the two failing checks in the sketch against the classes they exercise
before changing either.

## What the run cost, and what that says about the tooling

The first attempt, through `tools/night.sh` with a 180 s budget, produced no far-side report
at all and left the board in the **bootloader**. The second, given 420 s, passed 3.1 well
inside it.

The reading that fits both -- **not measured, and marked as such** -- is that the first far
side is slow because it lays out the queue and journal regions on a chip that has never held
them, and that it overran two separate 180 s limits: `night.sh`'s budget for the step, and
the sketch's own dead man's window, which nothing pokes while that far-side work runs in a
single `loop()` iteration.

`night.sh` now gives the step 600 s. The window inside the sketch is untouched and remains a
way for a slow first run to end in DFU.
